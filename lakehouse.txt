Lakehouse for Agents — Architectural Case

---
Why a Lakehouse changes what agents can do

Your current RAG architecture (S3 raw → embeddings → OpenSearch → agent)
handles one thing well: vector retrieval. A lakehouse replaces the fragmented storage l
ayer with a single, unified data platform that agents can query across every
data type — structured, semi-structured, and unstructured — with transactional guarantees.

---
The Core Architectural Shift

Without lakehouse (current):
OpenSearch  ←  vector queries only
DynamoDB    ←  session/audit only
S3 raw      ←  no queryable structure
Agent has no way to join structured + unstructured at query time

With lakehouse:
Bronze (S3 + Parquet/Delta)   raw ingestion, immutable, all sources
Silver (Delta Lake / Iceberg)  cleaned, chunked, enriched, embeddings stored alongside structured data
Gold (pre-computed)            agent-ready features, aggregations, vector indexes

Agent queries:
  → SQL via Athena/DuckDB       → structured facts (CMDB, SYSID, metrics)
  → vector search via LanceDB   → reads directly from Delta/Parquet, no separate DB
  → time travel query           → what did this service's blast radius look like 30 days ago?
  → join structured + vector    → enrich retrieved chunks with live CMDB metadata at query time

---
6 Specific Advantages for Agents

1. Structured + Unstructured in One Query
Agents today choose: vector search OR SQL. With lakehouse, a single agent tool can ask:
 "retrieve the top-5 policy chunks for parental leave AND join with the employee's HR record to
 check eligibility" — one query, one layer.

2. Time Travel — Agents Can Reason About Historical State
Delta Lake and Iceberg track every version of every table. An agent can query:
- What was the scorecard for payments-service on the day it was promoted to production?
- What did the blast radius graph look like before the outage?
This is impossible with OpenSearch or a pure vector DB.

3. Agent Writes Back — ACID Transactions
When an agent makes a decision or updates a record
(CMDB, catalog, audit log), S3 alone has no transactional guarantees —
 concurrent writes corrupt. Delta Lake gives full ACID on S3.
 Every agent action is committed atomically with a tamper-proof transaction log. Critical for SOX compliance.

4. Cost at Scale

┌──────────────────────┬─────────────┬───────────────┐
│        Store         │ 10M chunks  │  100M chunks  │
├──────────────────────┼─────────────┼───────────────┤
│ OpenSearch           │ ~$3K/month  │ ~$30K/month   │
├──────────────────────┼─────────────┼───────────────┤
│ Pinecone             │ ~$2K/month  │ ~$20K/month   │
├──────────────────────┼─────────────┼───────────────┤
│ S3 Parquet + LanceDB │ ~$250/month │ ~$2,500/month │
└──────────────────────┴─────────────┴───────────────┘

LanceDB stores vectors natively in Parquet/Lance format on S3. No separate vector DB service.
Agents query it directly.

5. Pre-Computed Feature Layer (Gold Layer)
Instead of agents recomputing the same aggregations on every query — blast radius scores,
service health signals, CMDB relationship subgraphs — these are pre-computed nightly into
Gold layer Delta tables. Agents read fast, structured facts instead of doing expensive inference work at
query time.

6. Unified Audit Trail
Every agent query, retrieved chunk, LLM response, tool call, and latency measurement written as a
Delta table row. Immutable. Queryable by Spark/Athena. Ready for compliance reports without
building a separate logging system.

---
What Needs to Happen Architecturally

Phase 1 — Foundation
  ├── Adopt open table format: Delta Lake (OSS) or Apache Iceberg
  ├── Land all raw sources in Bronze as Parquet on S3
  ├── Glue Data Catalog or Hive Metastore as the unified metadata layer
  └── Athena or DuckDB for serverless SQL queries from agent tools

Phase 2 — Silver Layer
  ├── ETL pipeline: clean, chunk, embed documents → store in Silver Delta table
  │   columns: chunk_id, content, embedding[], source, last_updated, allowed_groups[]
  ├── Structured enrichment: join CMDB / SYSID / ServiceNow into same Silver table
  └── LanceDB reads directly from Silver Parquet for vector queries

Phase 3 — Gold Layer (Agent-Ready)
  ├── Pre-computed features: blast radius scores, dependency graphs, service health
  ├── Materialized views for common agent queries (no re-computation at runtime)
  └── Agent audit log table: Delta, ACID, immutable

Phase 4 — Agent Integration
  ├── Two agent tools replace OpenSearch:
  │     sql_query(table, filters)     → Athena/DuckDB over Gold layer
  │     vector_search(query, top_k)   → LanceDB over Silver embeddings
  ├── Agents can JOIN across both in a single reasoning step
  └── All agent writes go through Delta transactions

---
The CIO Pitch in One Sentence

▎ A lakehouse gives agents a single, governed, auditable data layer that is 80% cheaper than
separate vector and structured stores, supports time travel for compliance, and lets agents reason
across structured facts and unstructured documents in the same query — capabilities that are
impossible with a pure vector DB architecture.

❯ will lake house seit in top of multiple vector databases.

No — it's the opposite relationship. A lakehouse sits below vector databases, not on top of them.

┌─────────────────────────────────────┐
│         Agent / Query Layer         │  ← agents query here
└──────────┬──────────────────────────┘
           │
     ┌─────┴──────┐
     │ Vector DB  │  ← OpenSearch, Pinecone, LanceDB
     │ (index)    │     built FROM the lakehouse
     └─────┬──────┘
           │ populated by pipeline
     ┌─────┴──────┐
     │  Lakehouse │  ← Delta Lake / Iceberg on S3
     │ (truth)    │     Bronze → Silver → Gold
     └────────────┘

The lakehouse is the source of truth. Vector databases are derived indexes built from it.

Think of it like a relational database and a search index — the database (lakehouse)
is authoritative, the search index (vector DB) is a materialized view for fast retrieval.
When the lakehouse changes, the pipeline re-syncs to the vector DB.

---
The practical patterns:

┌───────────────────────────────────┬────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│              Pattern              │                                                                      What happens                                                                      │
├───────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Lakehouse replaces vector DB      │ Embeddings stored as a column in Delta/Parquet. LanceDB queries them directly. No separate vector DB.                                                  │
├───────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Lakehouse feeds multiple vector   │ Silver layer holds canonical chunks + embeddings. Pipeline syncs to OpenSearch (for hybrid BM25+vector), Pinecone (for scale), etc. Each is a derived  │
│ DBs                               │ index.                                                                                                                                                 │
├───────────────────────────────────┼────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Federation across vector DBs      │ A query engine like Trino or Spark federates queries across multiple vector stores. The lakehouse is still the source — this is rare and complex.      │
└───────────────────────────────────┴────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

---
The reason this matters for agents:

If you have 3 vector databases (one per domain — HR, Legal, Engineering) with no lakehouse underneath,
you have 3 separate sources of truth. When a document changes, you update 3 indexes independently.
Drift happens. Agents get inconsistent results.

With a lakehouse underneath, there is one Silver table. The 3 vector DBs are all built from it.
Document changes in one place, all indexes re-sync from the same source. Agents always get consistent
data regardless of which vector index they hit.

❯ what is lancedb

LanceDB is a vector database that stores embeddings directly in Parquet/Lance files on S3 (or local disk) — no server, no separate service, no infrastructure to manage.

---
What makes it different from Pinecone / OpenSearch:

┌──────────────────────┬─────────────────────────────────┬────────────────────────────────────────┐
│                      │      Pinecone / OpenSearch      │                LanceDB                 │
├──────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ Deployment           │ Managed service / cluster       │ Embedded library (import in Python)    │
├──────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ Storage              │ Proprietary / OpenSearch shards │ Parquet/Lance files on S3              │
├──────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ Cost                 │ $2K–$20K/month at scale         │ S3 storage cost only (~$23/TB/month)   │
├──────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ Server               │ Yes — always running            │ No server — query runs in your process │
├──────────────────────┼─────────────────────────────────┼────────────────────────────────────────┤
│ Lakehouse compatible │ No (separate system)            │ Yes — reads native Parquet             │
└──────────────────────┴─────────────────────────────────┴────────────────────────────────────────┘

---
How you use it:

import lancedb

db = lancedb.connect("s3://my-bucket/vectors")
table = db.open_table("policy_chunks")

results = table.search(query_embedding).limit(5).to_pandas()

That's it. No API key. No cluster. The vectors live in S3 as Lance/Parquet files. The search runs locally in the process that calls it.

---
Why it matters for a lakehouse architecture:

Your Silver layer already stores chunks + embeddings as Parquet in S3. LanceDB reads that directly — no pipeline needed to sync data from your lakehouse into a separate vector service. The lakehouse table is the vector database.

The alternative (OpenSearch) requires: lakehouse → sync pipeline → OpenSearch cluster → agent queries OpenSearch. Two systems, two costs, drift risk between them.

With LanceDB: lakehouse → agent queries LanceDB which reads the same S3 files. One system.

---
The tradeoff: LanceDB is excellent up to ~100M vectors. Beyond that, or if you need real-time concurrent writes at very high throughput, a managed service like Pinecone or OpenSearch scales better. For most enterprise RAG workloads, LanceDB is sufficient and dramatically cheaper.

❯ parquet format

Parquet is a columnar file format for storing structured and semi-structured data efficiently. It's the standard storage format for data lakes and lakehouses.

---
Row format vs Columnar format — the key difference:

ROW format (CSV, JSON):
Row 1:  chunk_id=abc, content="PTO policy...", embedding=[0.02, -0.04, ...], source=confluence
Row 2:  chunk_id=def, content="FMLA rules...",  embedding=[0.11,  0.03, ...], source=sharepoint
Row 3:  chunk_id=ghi, content="Leave policy..", embedding=[0.07, -0.01, ...], source=confluence

To read just the `source` column — you must read all 3 full rows first.

COLUMNAR format (Parquet):
chunk_id column:  [abc, def, ghi]
content column:   ["PTO policy...", "FMLA rules...", "Leave policy..."]
embedding column: [[0.02,-0.04,...], [0.11,0.03,...], [0.07,-0.01,...]]
source column:    [confluence, sharepoint, confluence]

To read just the `source` column — read only that column's bytes. Skip the rest.

---
Why this matters:

┌────────────────────┬──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┐
│      Benefit       │                                                        What it means                                                         │
├────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Compression        │ Similar values in a column compress together. A text column of policy chunks compresses 5–10x better than row format         │
├────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Column pruning     │ Agent queries source and chunk_id only — Parquet skips reading the 1536-dim embedding column entirely. Massive I/O reduction │
├────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Predicate pushdown │ Filter WHERE source = 'confluence' evaluated before reading data into memory                                                 │
├────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Schema enforcement │ Types defined per column. No silent type mismatches                                                                          │
├────────────────────┼──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┤
│ Splittable         │ Large files split across Spark workers naturally                                                                             │
└────────────────────┴──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────┘

---
What a Silver layer Parquet file looks like for RAG:

chunk_id        STRING     "hr-policy-pto-v3-chunk-12"
content         STRING     "Employees may carry over up to 5 days..."
embedding       ARRAY<FLOAT>  [0.021, -0.043, 0.018, ...]   ← 1536 dims
source_system   STRING     "confluence"
source_url      STRING     "https://wiki.company.com/HR/PTO"
last_updated    DATE       2026-06-01
allowed_groups  ARRAY<STRING>  ["all-employees"]
sysid           STRING     "SYSID-06534"

Stored as one Parquet file. LanceDB reads the embedding column for vector search. Athena reads source_system, sysid, last_updated for SQL queries. Same file, different columns, zero duplication.

---
Parquet vs other formats:

┌─────────┬─────────────────────────────────────┬───────────────────────────────────────┐
│ Format  │              Good for               │                Bad for                │
├─────────┼─────────────────────────────────────┼───────────────────────────────────────┤
│ CSV     │ Human-readable, simple              │ No types, no compression, no columnar │
├─────────┼─────────────────────────────────────┼───────────────────────────────────────┤
│ JSON    │ Flexible schema                     │ Verbose, slow to query at scale       │
├─────────┼─────────────────────────────────────┼───────────────────────────────────────┤
│ Avro    │ Row-based streaming (Kafka)         │ Analytical queries                    │
├─────────┼─────────────────────────────────────┼───────────────────────────────────────┤
│ Parquet │ Analytical queries, lakehouse       │ Not human-readable, not streaming     │
├─────────┼─────────────────────────────────────┼───────────────────────────────────────┤
│ ORC     │ Similar to Parquet (Hive ecosystem) │ Less tooling than Parquet             │
└─────────┴─────────────────────────────────────┴───────────────────────────────────────┘

Parquet is the default format for S3, Glue, Athena, Spark, DuckDB, Delta Lake, and Iceberg. When people say "store it in the lakehouse" — they mean Parquet on S3.
