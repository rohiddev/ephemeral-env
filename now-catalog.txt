The risk without a deliberate approach is that catalog-info.yaml and now.yaml become two separate maintenance burdens with overlapping fields that drift from each other. The opportunity is to make them two outputs from one source of truth.

The Core Design Principle

One record per service. Two files. Two consumers.

Design decision: CMDB is the master. Both files are generated from it, not hand-authored independently. Any field that lives in both files should only be editable in one place — CMDB — and propagated outward.

Maximum Company Value — The Compound Effect
Neither file alone delivers the full value. Together they create something neither can do independently:
Scenario 1 — Developer Onboards to a New Service

Opens IDP, finds the service → catalog-info.yaml tells them: owner, system, CI/CD history, runbook, on-call
No need to ask anyone. Onboarding time: minutes not days

Scenario 2 — P1 Incident Fires

Database CI goes unhealthy → now.yaml relationships tell ITOM: 12 services depend on this
ITOM AIOps correlates into one incident, auto-assigns to DB team
SRE opens IDP Blast Radius tab → sees the same dependency graph from the developer side
Parallel tracks: ops working the DB, service teams notified automatically

Scenario 3 — Pre-Release Change Risk

Developer about to deploy a breaking API change
IDP Blast Radius (from catalog-info.yaml) shows: 4 services consume this API
ITOM (from now.yaml) shows: 2 of those services are Tier 1
Change request auto-raised in ServiceNow. Right approvers notified.

Scenario 4 — Leadership Asks "How Healthy Is Our Estate?"

IDP scorecard (from catalog-info.yaml): 87% of services have complete catalog entries
CMDB dashboard (from now.yaml): 94% CI registration, 78% dependency coverage
SBOM drift: 3.2% drift rate, 91% suppressed as false positives
One number: Platform health score — composite of both


Governance Model to Keep Both Files Healthy
At Repo Creation (automated)

IDP scaffolder generates catalog-info.yaml skeleton
Batch program generates now.yaml skeleton from CMDB
Both PRs raised simultaneously — team reviews and enriches

Ongoing (team-maintained)

Team owns relationship declarations in now.yaml
Team owns TechDocs and on-call info in catalog-info.yaml
IDP scorecard gates: incomplete files = scorecard penalty
SBOM nightly: drift flagged, team resolves via suppression workflow

Quarterly (platform-enforced)

Suppression auto-expiry review (90 days)
Scorecard thresholds reviewed and tightened
CMDB accuracy audit — now.yaml vs actual runtime dependencies


What to Build Next (Recommended Sequence)

Lock the shared field schema — agree on App Key, owner, tier, lifecycle conventions before bulk generation. A mismatch here is expensive at 20k repos.
Build the scorecard gates — IDP scorecard should enforce: both files present, required fields populated, at least one dependency declared in now.yaml.
Single PR trigger — when a new repo is created via IDP, both files should be generated and PRed in the same pipeline run, not separate processes.
Blast Radius as the showcase — the IDP Blast Radius tab, fed by both files, is the most visible proof point for leadership. Prioritise getting that live for the November capstone.
SBOM pipeline as the quality gate — once both files are in repos at scale, the nightly SBOM run keeps them honest without any manual effort.
