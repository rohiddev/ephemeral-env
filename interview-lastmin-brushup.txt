   ↓
URL Shortener

                     Analytics

User A ←── WebSocket ──→ Chat Server

173. File Storage Service

Think Google Drive or Dropbox.

Don't put huge files directly into a normal database.

User
 ↓
API
 ├──→ Object Storage → actual file
 |
 └──→ Database → filename, owner, permissions, location

Object storage could be Amazon S3.

The database stores metadata, while object storage stores the actual file.

Key concepts: object storage, metadata, permissions, versioning, encryption.

1. Circuit Breaker ⚡
Problem

Service A calls Service B, but Service B is down.

Without a circuit breaker:

Service A → Service B ❌
Service A → Service B ❌
Service A → Service B ❌
Service A → Service B ❌

Service A keeps trying and wastes resources.

Circuit breaker
Service A → Circuit Breaker → Service B ❌

After enough failures, the circuit breaker says:

"Stop calling Service B for now."

Service A → Circuit Breaker 🚫
                    X
                 Service B

After some time, it tests Service B again.

Think:

Circuit breaker = stop calling a service that is clearly failing.

Architecture benefit: prevents cascading failures.

2. Rate Limiter 🚦
Problem

One customer sends:

10,000 requests/second

Your API gets overwhelmed.

A rate limiter says:

"You can only make 100 requests per minute."

User
 |
100 requests → ✅
101st request → ❌
Example
Internet
   |
   ↓
Rate Limiter
   |
   ↓
API

Used for:

API protection
DDoS mitigation
Preventing abuse
Protecting backend systems
Think:

Rate limiter = traffic cop controlling how much traffic enters.

3. Bulkhead 🚢

This is one of the most important resilience patterns.

Imagine a ship has separate compartments.

If one compartment floods:

+---------+---------+---------+
|   OK    | FLOODED |   OK    |
+---------+---------+---------+

The entire ship doesn't sink.

Same idea in software.

Suppose:

Application
 |
 +--- Payment
 |
 +--- Email
 |
 +--- Reporting

If Reporting consumes all the CPU:

Reporting → consumes everything ❌
Payment → ❌
Email → ❌

With bulkheads:

Payment    → Resource Pool A
Email      → Resource Pool B
Reporting  → Resource Pool C

Reporting can fail without taking down Payment.

Think:

Bulkhead = isolate resources so one problem doesn't bring down everything.

4. Retry 🔄

Sometimes a request fails because of a temporary problem.

Service A → Service B
             ↓
           timeout

Instead of immediately giving up:

Try 1 → FAIL
Try 2 → FAIL
Try 3 → SUCCESS

But you don't want to retry endlessly.

Usually use exponential backoff:

Retry 1 → wait 1 second
Retry 2 → wait 2 seconds
Retry 3 → wait 4 seconds
Retry 4 → wait 8 seconds
Think:

Retry = try again because the failure might be temporary.

⚠️ Don't blindly retry every operation—especially non-idempotent operations like charging a credit card.

5. Timeout ⏰

Suppose Service A calls Service B.

Service B never responds.

Without timeout:

Service A
   |
   | waiting...
   | waiting...
   | waiting...
   | waiting...

Eventually all your application threads may get stuck.

With timeout:

Call Service B
     |
     | wait 3 seconds
     ↓
   TIMEOUT
     |
     ↓
Stop waiting
Think:

Timeout = don't wait forever.

6. Cache Aside 🗄️

This is extremely common with Redis + database.

Suppose you need customer information.

First check cache:

Application
    |
    ↓
 Redis
    |
    ↓
Found? → YES → return data

If not found:

Application
    |
    ↓
 Redis
    |
   MISS
    |
    ↓
Database
    |
    ↓
Get data
    |
    +----→ Redis
    |
    ↓
Application
Think:

Cache Aside = check cache first; if missing, get it from the database and put it into cache.

7. Write-Through Cache

Here, when you update data, you update the cache and database together.

Application
    |
    ↓
Cache
    |
    ↓
Database

For example:

Change customer address
        |
        +----→ Cache
        |
        +----→ Database

The goal is to keep the cache and database synchronized.

Think:

Write-through = update cache and database when you write.

8. Publish-Subscribe 📢

Think of a radio station.

The radio station publishes:

"New payment completed!"

Many listeners receive it.

In software:

                 Kafka
                   |
        "PaymentCompleted"
          /        |        \
         ↓         ↓         ↓
      Email     Fraud     Analytics
      Service   Service    Service

The Payment Service doesn't need to directly call all three services.

It publishes an event.

Think:

Pub/Sub = one event → many interested consumers.

This is very important for Kafka/event-driven architecture.

9. Event Sourcing 📖

Instead of storing only the current state, store every change that happened.

Normal database:

Account balance = $500

Event sourcing:

Deposit $1,000
Withdraw $200
Deposit $100
Withdraw $400

You can reconstruct:

1000 - 200 + 100 - 400 = $500

Why is this powerful?

You have a complete history.

For financial systems:

Transaction 1
Transaction 2
Transaction 3
Transaction 4
...

You can audit exactly what happened.

Think:

Event sourcing = don't just store the current state; store the history of changes.

10. CQRS

CQRS means:

Command Query Responsibility Segregation

Don't let the complicated name scare you.

It means:

Separate writing from reading.

Normally:

Application
    |
    ↓
One Database
    ↑
Read + Write

With CQRS:

             Application
             /         \
            ↓           ↓
        WRITE          READ
          |              |
          ↓              ↓
    Write Model      Read Model

Why?

Suppose your system has:

1 million reads
10,000 writes

You may want to optimize the read side separately.

Think:

CQRS = separate the system that writes data from the system that reads data.

11. Strangler Fig 🌳

This is a legacy modernization pattern.

Imagine you have a huge old application:

       OLD MONOLITH
+-------------------------+
| Customer                |
| Payment                 |
| Orders                  |
| Reporting               |
| Inventory               |
+-------------------------+

Don't rewrite everything at once.

Instead:

OLD MONOLITH
    |
    +---- Customer → NEW SERVICE
    |
    +---- Payment  → OLD
    |
    +---- Orders   → NEW SERVICE
    |
    +---- Reporting → OLD

Over time:

Old Monolith
     ↓
Smaller
     ↓
Smaller
     ↓
Eventually retired
Think:

Strangler Fig = gradually replace the old system instead of doing a risky big-bang rewrite.

This is extremely useful in enterprise architecture.

12. Saga Pattern ✈️🏨🚗

This is probably the hardest one.

Imagine booking a vacation:

1. Book flight
2. Book hotel
3. Book rental car

There is no single database transaction across all three systems.

Suppose:

Flight ✅
Hotel  ✅
Car    ❌

What do you do?

Saga says:

Undo the successful steps using compensating actions.

Book Flight ✅
     ↓
Book Hotel ✅
     ↓
Book Car ❌
     ↓
Cancel Hotel
     ↓
Cancel Flight

The cancellation operations are called compensating transactions.

Think:

Saga = coordinate a multi-step business transaction across multiple services without requiring one giant database transaction.

. Scalability — "How do I handle more users?"

Suppose your application currently handles:

1,000 users

Tomorrow it needs to handle:

1,000,000 users

You need to scale.

Load Balancer

Distributes users across multiple servers:

                 Load Balancer
                /      |      \
               ↓       ↓       ↓
            Server   Server   Server

Think: "Spread the traffic."

Horizontal Scaling

Add more servers:

1 server → 10 servers → 100 servers

Think: "Add more workers."

Caching

Don't repeatedly ask the database for the same information.

User → Cache → Data
          ↑
       fast

Think: "Keep frequently used information nearby."

Sharding

Split a huge database into multiple pieces.

             Database
                |
       +--------+--------+
       |        |        |
    Shard 1  Shard 2  Shard 3
    Users    Users    Users
    1-1M     1-1M     1-1M

Think: "Divide the database workload."

Interview sentence

"For scalability, I'd horizontally scale application instances behind a load balancer, use caching to reduce database load, and consider database sharding when the database itself becomes the bottleneck."

2. Reliability — "How do I keep the system running?"

Imagine one service fails.

You don't want the entire application to fail.

Replication

Have multiple copies:

        Application
        /    |    \
      Copy Copy Copy

If one fails:

Copy 1 ❌
Copy 2 ✅
Copy 3 ✅
Timeout

Don't wait forever:

Call Service
     ↓
Wait 3 seconds
     ↓
TIMEOUT
Retry

Try again if the failure might be temporary:

Try → Fail
Try → Fail
Try → Success

Usually with exponential backoff.

Circuit Breaker

If the service is clearly failing:

Service A → Service B ❌


Circuit opens
      ↓
STOP calling B temporarily
Bulkhead

Keep failures isolated:

Payment → Resource Pool A
Email   → Resource Pool B
Search  → Resource Pool C

If Search has a problem, it doesn't consume all resources needed by Payment.

Interview sentence

"For reliability, I'd use multiple instances for redundancy and combine timeouts, controlled retries, circuit breakers, and bulkheads to prevent cascading failures."

3. Performance — "How do I make it faster?"

Suppose your application takes:

2 seconds

but you want:

100 milliseconds
CDN

Put static content close to the user:

Phoenix User
     ↓
Nearby CDN
     ↓
Image

Instead of:

Phoenix User
     ↓
Server across the country
     ↓
Image
Caching

Keep frequently requested data in something fast like Redis.

Application → Redis

instead of constantly:

Application → Database
Database Index

Think of a book.

Without an index:

Search every page.

With an index:

Go directly to the page.

Same idea:

Without index → scan many rows
With index    → find matching rows quickly
Read Replicas

If you're doing millions of reads:

             Primary DB
              /      \
             ↓        ↓
        Read Replica Read Replica

Writes go to the primary; reads can be distributed to replicas.

Interview sentence

"For performance, I'd use CDN and caching for frequently accessed content, database indexes for efficient queries, and read replicas to scale read-heavy workloads."

4. Consistency — "Do all users see the same data?"

This becomes important when you have multiple servers/databases.

Suppose you update:

Bank balance = $1,000

Should every server immediately show:

$1,000

or is it acceptable if one server briefly shows:

$900

?

That's a consistency decision.

Strong consistency
WRITE
 ↓
All systems updated
 ↓
READ
 ↓
Latest value

Useful when correctness is critical.

Example:

Bank transaction.

Eventual consistency
WRITE
 ↓
Some systems updated
 ↓
Eventually
 ↓
All systems updated

Useful when a small delay is acceptable.

Example:

Social media likes.

You might see:

1,000 likes

while another server briefly shows:

999 likes
5. CAP Theorem

For distributed systems, CAP is about:

Consistency
Availability
Partition tolerance

The important interview idea:

When there's a network partition, you generally have to choose between stronger consistency and availability.

Don't simply say:

"You can only have two of the three."

That's an oversimplification.

Think:

Network problem
      ↓
Systems can't communicate
      ↓
Do I:
  A) reject requests to preserve consistency?
or
  B) continue serving requests and reconcile later?

That is the architectural decision.
