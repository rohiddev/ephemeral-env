OPA as an enterprise policy layer works by evaluating declarative Rego policies at decision points throughout your stack. Here's how it maps across your four domains:

  ---
  OPA Enforcement Points — Enterprise Map

  1. Harness Pipelines (Policy as Code)

  Harness has native OPA integration — policies evaluated before a pipeline can run or a resource is saved.

  Pipeline YAML submitted → Harness calls OPA → allow/deny → pipeline executes

  What you enforce:
  - Required stages (e.g. security scan must exist before deploy)
  - Approved image registries only
  - Mandatory approval stages for prod
  - Branch restrictions (only main deploys to prod)
  - Required variable declarations (e.g. cost_center must be set)

  Where: Harness > Platform > Governance > Policies. Rego policies, evaluated on pipeline_execution or pipeline_save events.

  ---
  2. Kubernetes (OPA Gatekeeper)

  OPA runs as an admission webhook via Gatekeeper — every kubectl apply is evaluated.

  kubectl apply → API server → Gatekeeper webhook → OPA policy → admit/reject

  What you enforce:
  - All pods must have team and service labels
  - No latest image tags
  - CPU/memory limits required
  - Approved container registries only
  - No hostNetwork: true without exception annotation
  - Namespace quota and naming conventions

  Implementation:
  - ConstraintTemplate (defines the Rego rule schema)
  - Constraint (instance — applies template to target namespaces/resources)

  ---
  3. Cloud Infrastructure (Terraform + conftest)

  OPA evaluated against Terraform plan JSON before terraform apply.

  terraform plan -out=plan.tfplan
  terraform show -json plan.tfplan | conftest test -

  What you enforce:
  - All AWS resources must have Owner, CostCenter, Environment tags
  - S3 buckets cannot be acl: public-read
  - Security groups cannot open 0.0.0.0/0 on port 22
  - Only approved regions (e.g. us-east-1, eu-west-1)
  - EC2 instances must use approved AMI IDs

  In Harness pipelines: ShellScript step runs conftest test and fails the stage on violation.

  ---
  4. Harness IDP (Catalog + Workflow Governance)

  This is the integration point you own. Two layers:

  Catalog Governance:
  - Every catalog-info.yaml validated on ingestion
  - Required fields: spec.owner, spec.system, metadata.tags
  - Naming conventions on metadata.name
  - now.yaml presence required before catalog-info.yaml (your production readiness gate)

  Workflow Governance:
  - Who can trigger which workflows (RBAC + OPA)
  - Prevent workflows from bypassing required fields
  - Audit trail: every workflow execution logged with user identity

  Yes. Implement it as one policy model with multiple enforcement tiers.

  1. Tier 1 — IDP: front-door validation

  Use Harness IDP workflows as the first checkpoint.

  Before a developer creates anything, the IDP form should validate:

  SYSID is present
  owner is valid
  cost center is present
  environment is selected
  repo name follows naming standard
  requested platform/resource is allowed
  required approvals are identified

  The IDP should call a pre-flight policy API or conftest/OPA service before the workflow proceeds.

  Goal: catch problems early in the form, not later in pipeline logs.

  Your own model already says IDP can pre-validate intent before downstream OPA checks and surface clearer user-facing messages.

  2. Tier 2 — Catalog: ownership and metadata governance

  Every service must have a valid catalog-info.yaml.

  Enforce required fields:

  metadata:
    name: loan-app
    tags:
      - tier:critical
  spec:
    owner: lending-platform-team
    system: loan-processing

  Validate:

  metadata.name
  spec.owner
  spec.system
  metadata.tags
  SYSID
  lifecycle
  dependencies
  APIs
  databases
  Kafka/MQ/SFTP relationships

  Goal: no service enters the catalog without ownership and dependency visibility.

  3. Tier 3 — Harness Pipeline: delivery governance

  Use Harness Governance / OPA policies on:

  pipeline save
  pipeline execution

  Enforce:

  security scan stage exists
  artifact comes from approved registry
  production deploy has approval
  branch restriction: only main or release branch to prod
  required variables exist: sysid, cost_center, owner, environment
  pipeline uses standard templates

  Your pasted architecture correctly states Harness policies can evaluate before pipeline run or save.

  4. Tier 4 — Terraform: infrastructure governance

  Before terraform apply, run:

  terraform plan -out=plan.tfplan
  terraform show -json plan.tfplan > plan.json
  conftest test plan.json

  Enforce:

  mandatory tags
  approved regions
  no public S3 buckets
  no SSH open to 0.0.0.0/0
  approved AMIs only
  encryption enabled
  backup policy present
  production resources require approval

  Goal: no non-compliant infrastructure gets created.

  5. Tier 5 — Kubernetes: runtime admission control

  Use OPA Gatekeeper or similar admission control.

  Enforce:

  no latest image tag
  CPU/memory limits required
  approved registries only
  required labels:
  app
  owner
  sysid
  environment
  no privileged containers
  no hostNetwork: true
  namespace naming standards
  sidecar requirements

  Your document correctly maps Kubernetes enforcement through Gatekeeper admission checks.

  6. Tier 6 — Runtime / Observability: continuous validation

  After deployment, validate continuously:

  service has logs
  traces are emitted
  dashboards exist
  alerts exist
  ownership is visible
  CMDB/catalog relationship is correct
  blast-radius data is complete

  This is where IDP + catalog + observability come together.
