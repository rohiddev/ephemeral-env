 Step 1 — What the SBOM JSON looks like

  CycloneDX format (from cdxgen/syft/GitHub):

  {
    "bomFormat": "CycloneDX",
    "components": [
      { "name": "kafka-clients",     "version": "3.4.0", "purl": "pkg:maven/org.apache.kafka/kafka-clients@3.4.0" },
      { "name": "pg",                "version": "8.11.0", "purl": "pkg:npm/pg@8.11.0" },
      { "name": "spring-boot-web",   "version": "3.2.1",  "purl": "pkg:maven/org.springframework.boot/spring-boot-web@3.2.1" }
    ]
  }

  Every dependency — direct and transitive — is listed as a component with a name and purl.

  ---
  Step 2 — Map packages → technology flags

  A script reads the SBOM and checks component names against known signatures:

  # .github/scripts/sbom_to_flags.py
  import json, sys

  SIGNATURES = {
      "kafka":    ["kafka-clients", "spring-kafka", "confluent-kafka-python", "sarama", "franz-go"],
      "mq":       ["amqp", "rabbitmq-client", "ibm-mq-allclient", "activemq-client"],
      "database": ["pg", "mysql-connector-java", "pymongo", "hibernate", "go-sql-driver", "psycopg2"],
      "ftp":      ["commons-net", "ftplib", "jsch"],
      "api":      ["okhttp", "axios", "requests", "httpclient", "feign"],
  }

  sbom = json.load(open(sys.argv[1]))
  names = [c["name"].lower() for c in sbom.get("components", [])]

  flags = {tech: any(pkg in name for name in names for pkg in pkgs)
           for tech, pkgs in SIGNATURES.items()}

  print(json.dumps(flags, indent=2))

  Output — sbom-deps.json:
  {
    "kafka":    true,
    "mq":       false,
    "database": true,
    "ftp":      false,
    "api":      true
  }

  ---
  Step 3 — now.yaml declares what the team knows about

  The team's now.yaml (in their repo root):

  csdm: v1
  kind: BusinessService
  spec:
    cmdb_ci: "APP-06534"
    dependencies:
      - type: database
        description: "PostgreSQL customer records"
      - type: api
        description: "Payments gateway REST API"
    # kafka is missing — team forgot it

  ---
  Step 4 — Validate: SBOM detected vs now.yaml declared

  # .github/scripts/validate_deps.py
  import json, yaml, sys

  flags   = json.load(open(sys.argv[1]))     # sbom-deps.json
  now     = yaml.safe_load(open(sys.argv[2])) # now.yaml

  declared = {d["type"].lower() for d in now.get("spec", {}).get("dependencies", [])}

  failures = [
      f"SBOM detected '{tech}' but now.yaml declares no '{tech}' dependency"
      for tech, detected in flags.items()
      if detected and tech not in declared
  ]

  if failures:
      for f in failures:
          print(f"FAIL: {f}")
      sys.exit(1)

  print("OK: all detected dependencies declared in now.yaml")

  Developer sees in the PR check:
  FAIL: SBOM detected 'kafka' but now.yaml declares no 'kafka' dependency

  ---
  Step 5 — GitHub Actions wires it together

  # .github/workflows/sbom-validate.yml
  name: SBOM Dependency Validation
  on:
    pull_request:
      branches: [develop, qa, master]

  jobs:
    validate:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4

        - name: Generate SBOM
          run: cdxgen -o sbom.json .

        - name: Extract flags
          run: python3 .github/scripts/sbom_to_flags.py sbom.json > sbom-deps.json

        - name: Validate against now.yaml
          run: python3 .github/scripts/validate_deps.py sbom-deps.json now.yaml

  PR is blocked from merging until the team adds the missing dependency to now.yaml.

  ---
  Step 6 — False positive override

  If kafka-clients is pulled in by a framework but the service genuinely doesn't produce/consume Kafka messages:

  # sbom-overrides.yaml  (checked into repo, platform_engineering must approve PR)
  overrides:
    - tech: kafka
      package: kafka-clients
      reason: pulled in transitively by spring-cloud-stream, not used directly
      approved_by: platform_engineering

  Validation script checks for this file before failing:

  overrides_path = "sbom-overrides.yaml"
  if os.path.exists(overrides_path):
      overrides = yaml.safe_load(open(overrides_path))
      override_techs = {o["tech"] for o in overrides.get("overrides", [])}
      failures = [f for f in failures if not any(t in f for t in override_techs)]

  The override file itself requires a PR approved by platform_engineering — so it can't be self-approved.

  ---
  Where it sits in the bigger picture

  PR opened
    └── GitHub Actions: sbom-validate (blocks merge on mismatch)
  Merge to develop/qa/master
    └── Harness pipeline: scorecard check reads now.yaml completeness
        └── If now.yaml missing kafka → scorecard < 100% → prod deploy blocked

  Two gates: PR-level (catches it early) + deployment-level (final enforcement). The SBOM check at PR time means by the time code reaches the scorecard gate, now.yaml is already accurate.

❯ how difficlut is it to develop this script

⏺ The scripts themselves are simple — the hard parts are elsewhere.

  The scripts: 1 day

  What I showed is production-ready as-is. sbom_to_flags.py is ~25 lines, validate_deps.py is ~20 lines. Any Python developer can write and test these in a day. The GitHub Actions workflow is
  boilerplate.

  The package signature list: ongoing

  The SIGNATURES dict is where real effort sits. The list I wrote covers the most common packages but every language ecosystem has variants:

  - Java alone: kafka-clients, kafka_2.13, spring-kafka, kafka-streams, reactor-kafka
  - Go: sarama, franz-go, confluent-kafka-go, segmentio/kafka-go
  - Python: kafka-python, confluent-kafka, aiokafka

  You need someone to audit the actual packages in your 19K repos. Run jq '[.components[].name]' sbom.json | sort -u across a sample of repos and you'll see what's actually in use. That audit is
  a few days, not weeks.

  The blocker: now.yaml schema is not finalised

  The validate script assumes spec.dependencies[].type exists in now.yaml. That schema is still WIP (RapDev haven't confirmed it). You can't write the validation logic until the schema is locked.
   This is the real dependency.

  SBOM generation at scale: the actual hard problem

  Generating a reliable SBOM across 19K repos with mixed Java/Go/Python/Node is non-trivial:
  - cdxgen covers most languages but needs the right build tool present
  - Some repos won't have a lockfile → SBOM is incomplete
  - Monorepos need per-module SBOM, not one top-level scan

  Rolling this out to 19K repos is a platform problem, not a scripting problem. You'd start with a pilot of ~50 repos across different languages to find gaps before broad rollout.
