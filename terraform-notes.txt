 Easy parts

  Adding a new resource — just edit one YAML file and run two commands:
  # edit environments/idp-p2.yaml, add entry
  terraform apply -var-file=environments/p2.tfvars
  No code changes, no pipeline edits. This is as simple as it gets.

  Repeating a promotion — identical command, different env. Muscle memory after first run.

  ---
  Friction points

  First-time setup is manual and fiddly:
  - Fill account IDs into 3 YAML files
  - Create 3 tfvars files from examples
  - Vault token expires — need to re-authenticate every session
  - AWS SSO session also expires independently
  - terraform init -reconfigure easy to forget when switching envs — wrong state if skipped

  The null_resource trigger limitation:
  - If you update a workflow YAML in GitHub but don't change the identifier/branch, Terraform sees no-op and skips it
  - Requires a manual -replace flag to force re-run — not obvious to a new user

  No visibility into what's actually in Harness:
  - Terraform state only tracks that the curl ran, not what Harness accepted
  - If a registration fails silently, state says "done" but Harness doesn't have it
  - Must manually check the Harness UI to confirm

  ---
  Verdict

  Good for: Platform engineers who run it occasionally and know Terraform basics.

  Not great for: Anyone who needs to promote frequently, or teams who want a simple button-click experience.

  If you want simpler, the better UX would be a Harness pipeline with a workflow_dispatch-style trigger — select env, click run, done. No Vault token management, no init commands, no state to think
  about. That's the Harness IaC approach we discussed earlier.
