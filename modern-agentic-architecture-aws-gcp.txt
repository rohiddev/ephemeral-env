AWS Architecture

- Google ADK as the agent application framework / orchestration layer because ADK is open-source, supports multi-agent systems, offers structured workflows and dynamic routing, and is designed to be model-agnostic and deployment-agnostic.
- AWS / Amazon Bedrock as the enterprise AI backbone for foundation models,
RAG, managed knowledge bases, guardrails, private connectivity, IAM, and observability.

1) Executive summary

Think of the architecture in 4 big layers:

1. Experience layer – chat UI, portal, API, Slack/Teams bot, application integration.
2. Agent layer – a Google ADK supervisor agent plus several specialist agents (search agent, policy agent, troubleshooting agent, workflow agent, etc.).
ADK is a good fit here because it supports hierarchical multi-agent systems, custom tools, graph workflows, and evaluation/tracing.
3. Knowledge + action layer – Bedrock Knowledge Bases for RAG, plus enterprise tools/APIs (ServiceNow, Jira, CMDB, GitHub, databases, internal services).
Bedrock Knowledge Bases support managed ingestion/retrieval and can also use self-managed vector stores.
4. Platform layer – AWS security, observability, identity, networking, encryption, and policy controls using IAM,
CloudWatch, CloudTrail, KMS, PrivateLink, and Guardrails.

3) Recommended architecture by layer

A. Experience layer

Use a standard enterprise entry point:
- Internal portal / app UI for employees
- Chat interface (Teams/Slack/web app)
- Application API for system-to-system usage

This layer should send requests to your agent gateway / backend service, not directly to the models.
That keeps controls centralized and makes it easier to enforce policy, logging, and guardrails.
IAM federation and temporary credentials are the recommended access pattern for AWS service access.

What this gives you
- one entry point
- consistent auth
- request logging
- policy enforcement
- easier cost and usage tracking

B. Agent orchestration layer (Google ADK)

Use Google ADK for the application logic:

Recommended agent roles

1. Supervisor Agent
   - understands user intent
   - decides whether to answer directly, retrieve knowledge, call a tool, or delegate to another agent
2. RAG/Search Agent
   - retrieves documents from Bedrock Knowledge Bases
   - can perform multi-step retrieval for hard questions
3. Workflow/Action Agent
   - calls enterprise APIs
   - triggers jobs/workflows
   - gathers structured data from systems of record
4. Policy/Risk Agent
   - checks if the request is allowed
   - determines if additional approval or human review is needed
5. Domain Agents
   - HR agent
   - engineering platform agent
   - finance/procurement agent
   - operations agent
   - incident-response agent

ADK is a good fit because it supports specialized agent teams, workflow agents,
dynamic routing, tools/OpenAPI integrations, and built-in evaluation/observability concepts.
It is also designed to run locally or scale on managed runtimes / Kubernetes.

Where to run ADK on AWS

A practical enterprise choice is:
- EKS for large-scale shared platform deployments
- ECS/Fargate for simpler container operations
- optionally evaluate Bedrock AgentCore where you want managed runtime and observability for framework-based agents,
because AgentCore is designed for secure AI agent execution with runtime, memory, identity, and observability.

Simple rule:
ADK = brains/orchestration code
AWS = enterprise runtime, security, knowledge, logging, and model services

C. RAG layer (enterprise knowledge)

For RAG, Amazon Bedrock Knowledge Bases should be the primary retrieval service.

Why Bedrock Knowledge Bases

Bedrock Knowledge Bases can:
- ingest enterprise data
- handle chunking, embedding, indexing, and retrieval
- connect to sources like S3, SharePoint, Confluence, Google Drive, OneDrive, and web content
- enforce document-level permission filtering / ACLs
- support agentic retrieval and multi-hop reasoning
- integrate with observability tooling for retrieval traces and metrics

Recommended document sources
- S3 document lake
- SharePoint / Confluence
- internal wiki
- CMDB exports
- API specs / runbooks / SOPs
- incident reports
- policies and standards

Two RAG patterns to use

1. Classic RAG

Use when the question is straightforward:
- retrieve top relevant chunks
- pass context to the model
- answer with citations

2. Agentic RAG

Use for complex enterprise questions:
- supervisor decomposes the question
- RAG agent retrieves from multiple knowledge sources
- workflow agent calls APIs if real-time data is needed
- policy agent validates access and sensitivity
- final answer is synthesized

Bedrock Knowledge Bases explicitly support agentic retrieval, iterative retrieval, and multi-hop reasoning,
which is exactly what you want for enterprise-grade "find + reason + act" patterns.

D. Action / tool layer

This is where the system becomes agentic, not just informational.

Use ADK tools / OpenAPI integrations to connect to:
- ServiceNow
- Jira
- CMDB
- GitHub / CI-CD
- internal databases
- private REST services
- ticketing / approvals
- reporting systems

ADK supports custom tools and OpenAPI-based integrations, and Bedrock Agents support tools,
action groups, and knowledge bases for domain-specific execution.

Important enterprise rule:

Separate read-only retrieval from write/action tools.

For example:
- RAG/Search Agent = read
- Workflow Agent = controlled write / action
- Policy Agent = approval gate

This reduces risk and makes approvals easier.

4) Security architecture

For a large enterprise, this is the most important part.

Identity and access

Use:
- enterprise federation / SSO
- AWS IAM roles and temporary credentials
- least-privilege access policies
- resource-level Bedrock permissions where possible

Private networking

Use AWS PrivateLink / VPC endpoints for:
- Bedrock control plane
- Bedrock runtime
- Bedrock agent runtime

This keeps traffic private and avoids exposing traffic over the public internet.

If the agent must reach internal databases or private APIs, use private VPC connectivity
for the runtime/tool layer. Bedrock AgentCore provides VPC access options for secure outbound connectivity to private resources.

Encryption

Use:
- TLS in transit
- KMS-managed encryption for data at rest
- S3 encryption
- secrets in AWS Secrets Manager / parameter store
- CloudTrail logging for key service actions

Data protection for RAG

Use two security patterns depending on sensitivity:

Pattern A: Redact before indexing
- detect PII/PHI/confidential content
- redact before ingestion
- store only sanitized content in the knowledge store

Pattern B: Role-based retrieval
- keep sensitive content
- enforce ACL filtering at retrieval time
- only authorized users see sensitive passages

AWS specifically documents both pre-ingestion redaction and RBAC-based retrieval protection for Bedrock RAG architectures.

Guardrails

Use Amazon Bedrock Guardrails for:
- blocked topics
- sensitive-information detection
- contextual grounding checks
- policy enforcement
- monitoring interventions via CloudWatch

5) Observability architecture

For enterprise deployment, observability must cover:

1. Prompt / response tracing
2. Agent step tracing
3. Tool execution tracing
4. RAG retrieval tracing
5. Latency / cost / token usage
6. Policy / guardrail interventions
7. Error analysis and root cause

AWS-native stack

Use CloudWatch Generative AI Observability for:
- model usage
- latency
- errors

- prompt tracing
- visibility into models, tools, agents, and knowledge bases

If you use AgentCore-style runtime patterns, AgentCore Observability provides:

OpenTelemetry

Instrument your ADK services with OpenTelemetry / ADOT so traces can flow to:
- CloudWatch
- Datadog
- Dynatrace
- Grafana / Langfuse / Arize, etc.

AWS provides examples showing Amazon Bedrock agent traces exported to OpenTelemetry-compatible platforms.

What to log
- user id / role / tenant
- correlation id
- prompt class (not raw secrets)
- agent chosen
- tool called
- documents retrieved
- response latency
- tokens and cost
- human-override events
- guardrail interventions

6) Recommended enterprise deployment pattern

Start with 3 modes

Mode 1: Enterprise RAG assistant
- answer policy / SOP / knowledge questions
- read-only
- low-risk
- fastest to production

Mode 2: Agentic RAG
- answer + reason + fetch real-time context
- can combine KB search with API calls
- ideal for operations, platform engineering, and support

Mode 3: Action agents
- can create/update tickets, run workflows, gather evidence, or trigger automation
- requires stronger RBAC, approval, and audit trails

This phased approach lets you prove value early without exposing write-actions too soon.

7) A simple "golden architecture" recommendation

If I had to recommend one practical enterprise design, it would be this:
- Google ADK for agent coding/orchestration
- EKS or ECS/Fargate to run ADK services on AWS
- Amazon Bedrock for model inference
- Bedrock Knowledge Bases for managed RAG
- S3 + enterprise connectors as the document estate
- Bedrock Guardrails for safety/policy
- IAM + SSO + least privilege for access
- PrivateLink + VPC connectivity for private network paths
- CloudWatch + OpenTelemetry for observability
- CloudTrail + KMS + Secrets Manager for audit and security

That combination gives you:
- flexibility from ADK
- enterprise controls from AWS
- clean RAG foundation
- a path from chatbot → agentic assistant → controlled automation

Use Google ADK as the multi-agent control plane, use Amazon Bedrock as the secure enterprise AI substrate,
 use Bedrock Knowledge Bases for RAG, and wrap everything with AWS-native security, private networking, and
 CloudWatch/OpenTelemetry observability.

- line-of-business application,

Best practice: applications should call a centralized backend or agent gateway, not call models directly, so that identity, audit, policy, and observability remain centralized. This pattern aligns with Agent Platform's governance and management surfaces for agent identity, access, and monitoring.

B. Agent orchestration layer

Use ADK for the multi-agent implementation. ADK is designed for code-first development, multi-agent systems,
workflow agents, dynamic routing, and deployment to managed or containerized runtimes.

Recommended agent roles

1. Supervisor agent

The supervisor agent receives the user request, determines the intent, chooses which specialist agent should handle it, and coordinates the final response. This matches Google's model of ADK-based complex, multi-agent orchestrations with granular control.

2. RAG / search agent

This agent is responsible for retrieving trusted knowledge from enterprise data using Agent Search,

3. Action / workflow agent

This agent executes actions such as creating tickets, retrieving data from systems of record, invoking APIs, or coordinating tool calls. Agent Platform supports tools, external systems, MCP-based integrations, and code-first orchestration through ADK.

4. Policy / risk agent

This agent checks whether the request is allowed, whether sensitive data is involved,
and whether the workflow should proceed automatically or require additional approval.
Governance and policy enforcement are a first-class part of the Agent Platform lifecycle.

5. Domain specialist agents

Google gives you three strong options, depending on how much control you want:

Option 1: Agent Search

Use Agent Search if you want fast time-to-value and a Google-quality retrieval engine that already supports search,
enterprise document handling, grounding, and out-of-the-box RAG behavior.
Google explicitly describes Agent Search as a component for generative AI applications and as an out-of-the-box RAG system

Option 2: RAG Engine

Use RAG Engine if you want a managed orchestration service for RAG in production and enterprise-ready contexts,

Google describes RAG Engine as a fully managed runtime for RAG orchestration.

Option 3: Build-your-own retrieval

Use Vector Search + Embeddings + ranking / grounding APIs if you want maximum design control over parsing,
chunking, indexing, semantic retrieval, and ranking.
Google's RAG architecture guides explicitly describe this pattern for large-scale, production RAG systems.

5) RAG vs agentic RAG

Classic RAG

Classic RAG means:
- retrieve relevant documents,
- pass context to the model,
- generate an answer grounded in retrieved facts.

This is good for:
- policies,
- SOPs,
- runbooks,
- knowledge lookup.

Agentic RAG

Agentic RAG goes further. The system can:
- break a complex task into sub-questions,
- retrieve from multiple knowledge sources,
- call tools or APIs for live enterprise data,
- apply policy checks,
- then synthesize a final answer or action.

That is the better fit for a large enterprise because real enterprise tasks rarely depend on documents alone;
they usually require documents + live systems + approvals + business rules.

8) Security architecture

This is the part leadership will care about most.

A. Identity and access

Use Cloud IAM, service accounts, and controlled agent access so every deployed agent has a defined identity and scoped
permissions. Google documentation explicitly calls out agent identity and managed access as part of Agent Platform
operations and governance.

B. Data protection

Use CMEK where supported to control encryption, and use Google Cloud security controls designed for Gemini Enterprise Agent Platform and related ML services. Google documents CMEK and other security controls for the platform and related services.

C. Network isolation

For high-security enterprise deployments, use VPC Service Controls (VPC-SC) to reduce data exfiltration risk.
 Google documents VPC-SC support for Gemini Enterprise Agent Platform and explains secure perimeter-based deployment approaches.

If agents need to access private enterprise resources, use private connectivity patterns such as PSC-I / private
connectivity rather than broad public egress. Google's networking guidance for Agent Engine describes this model
for private resource access.

D. Secure retrieval

For RAG, keep access aligned with enterprise policy. Retrieval should only expose data that a given user or
agent is allowed to access. Google's grounding and enterprise retrieval offerings are designed around enterprise
data integration and grounded, trusted responses.

E. Governance and audit

Use platform governance plus cloud observability and audit surfaces so agent behavior is reviewable,
monitorable, and explainable in production. Google positions governance and optimization as core pillars of the platform.

10) Phased rollout for a large enterprise

Phase 1: Enterprise RAG assistant

Start with read-only knowledge answers grounded in enterprise content using Agent Search or RAG Engine.
This is the fastest, lowest-risk path.

Phase 2: Agentic RAG

Add orchestration across multiple sources and APIs using ADK-based specialist agents.
This is where the system becomes much more valuable for engineering, operations, and internal support.

Phase 3: Controlled action agents

Allow agents to take actions such as updating systems or launching workflows,
 but only behind policy checks, access controls, and production tracing.
 This aligns with Agent Platform's managed governance and optimization model.
